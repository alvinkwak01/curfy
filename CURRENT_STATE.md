# Curfy — current engineering state

Updated: 2026-11-02. Source of truth: current branch and device observations, not older claims in CONTEXT.md.

## Goal

At the user's configured bedtime, shield only the apps they explicitly selected using iOS Screen Time APIs, independent of whether Curfy is running. Complete the continuous 120-second hold before temporarily lifting the native shield, then restore shielding after the exception. The app starts with three user-chosen routine presets, each defining a single continuous daily restriction interval; all endpoint times are editable.

## Milestone: scoped one-app choice tickets, never an automatic unlock (2026-11-02)

**Goal:** prepare one native, opaque app token for a future Premium 120-second hold without unshielding anything, trusting JavaScript token identities, or letting a stale app-row selection act on a new protected-app list.

**Implemented:** `modules/curfy-protected-apps/ios/CurfyProtectedAppsModule.swift` adds `prepareProtectedApp` and `validatePreparedApp`. A strictly whitelisted committed selection must match its whole-selection revision and a valid row index. Swift creates a random UUID-based `curfy-single-app-...` ID with a **single** `ApplicationToken`, persisted in the pinned 0.6.1 App Group selection format. A separate native-only ticket records the source committed ID, revision, row index and creation date. Before any future exception, iOS must re-decode the saved singleton and confirm it equals the same token still in the current committed selection. Tickets expire for authorization after 10 minutes; orphaned scoped selections are pruned after 24 hours (enough to retain a token for an eventual 15-minute reblock monitor). The bridge returns ONLY the random scoped ID, never a token or app name. **Preparing and validating do not call ManagedSettings, unblock any app, or alter the live schedule.**

`modules/curfy-protected-apps/index.tsx` exposes typed, input-validating wrappers; `tests/protectedAppChoices.test.cjs` adds tests for successful preparation/revalidation, invalid drafts/indexes/revisions, platform restrictions and a source-level prohibition on unshield side effects. ## Milestone: three working protection routines, simpler onboarding and cutoff recovery (2026-11-02)

**User explicitly requested implementation for initial product, rather than deferral.** Source still uses one `curfy-bedtime` daily recurring iOS DeviceActivity schedule with two local clock boundaries. The internal legacy state names `bedtime` / `wakeTime` now represent **restriction start** / **apps available again**, not sleep measurements or mandatory wake-up times. No new native OS mode or second activity monitor is required for these continuous windows.

| User-facing selection | New-user suggested start | New-user suggested app availability | OS-level behavior |
| --- | --- | --- | --- |
| **In the evening** | 11:00 p.m. | 6:00 a.m. next day | Selected app shielded overnight; stops at cutoff |
| **In the morning** | 6:00 a.m. | 9:00 a.m. same day | Selected app shielded during chosen morning hours |
| **Both** | 11:00 p.m. | 9:00 a.m. next day | Same selected app shielded without any gap overnight and through morning |

Defaults are **editable suggestions**, not unchangeable rules. **3 a.m. is not a cutoff.** User selects actual *app available again* time, not self-reported sleep or wake time. Apple's daily recurring interval is at least 15 minutes, checked before saving. Morning does NOT run the evening "10 minutes before" reminders. New default in documentation applies only to newly selected routines, **existing installs preserve their saved 23–06 or customized times** and load legacy `evening` if no routine key exists.
